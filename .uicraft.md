# ZZZ Mod Manager · UI Craft Context

## Product and users

- Product: a local Windows WPF launcher and Mod manager for Zenless Zone Zero.
- Primary users: players who repeatedly scan, filter, enable, diagnose, and switch Mods, often while the game is already running.
- Core jobs: understand game/runtime readiness at a glance, locate a Mod quickly, distinguish immediate vs. reload-required changes, and perform safe actions with confidence.
- Supported window range: default 1280×820; minimum 1040×680. The interface must remain usable at the minimum size without horizontal page scrolling.

## Personality

The UI is an **ops console**: neutral ink surfaces, one decisive command accent, and semantic colors that each mean exactly one thing. It may echo ZZZ's high-contrast attitude through geometry and typography, but must not imitate noisy game menus or sacrifice readability.

## Design principles

1. **Status before decoration.** Runtime readiness, enabled state, pending/reload state, and errors are the strongest information signals.
2. **Two-second scan.** Page title, primary action, active filter, result count, and each card's state must be recognizable without reading paragraphs.
3. **Dense but breathable.** Use compact toolbars and cards with deliberate 4/8/12/16/24/32 spacing; avoid oversized empty panels.
4. **One clear primary action per region.** Launch/reload and enable/disable dominate; maintenance actions stay secondary.
5. **Never rely on color alone.** Pair color with labels, borders, dots, or text such as “已启用”, “需重载”, and “缺少依赖”.
6. **Stable desktop behavior.** Preserve keyboard focus, native scrolling, existing event handlers/control names, and all Mod-management semantics.

## Visual language

### Color roles

Every color below exists as a token in `Themes/DarkTheme.xaml`, whose light counterpart is `Themes/LightPalette.xaml`. Never write a raw hex value in a view, template, or view model; add or reuse a token instead. Both palettes declare the **same key set**: `LightPalette.xaml` carries colors only, while every brush, shape token, style, and template stays in `DarkTheme.xaml` and is repainted at runtime. The dark values below are normative; the light palette is their inversion and must preserve each role's meaning, not merely its hue.

- Canvas: neutral ink `#0C0D12`.
- Sidebar / deep surface: `#11131A`; sunken surface (inputs, tracks, inset counters) reuses the same value via `SurfaceSunken`.
- Surface: `#171922`; raised surface (cards): `#1E212B`; hover/selected surface: `#282C38`.
- Border: `#2F3441`; stronger border: `#464D5E`.
- Primary text: `#F3F5F9`; secondary text: `#ACB4C4`; quiet text: `#7E8798`.
- **Command accent** (primary actions, focus rings, navigation selection): iris `#8C7CFF`; pressed `#6F5CF5`; accent foreground `#0B0A18`; accent tint (selected row/chip fill) `#23204A`.
- **Success / enabled**: green `#3FCF8E` with foreground `#04170F`. Reserved exclusively for “已启用”-class state. It is never used for buttons, focus, or navigation.
- Warning / reload required / pending: amber `#E8A33D` with foreground `#1A1206`.
- Error / destructive: coral `#F2596F`, with dedicated destructive surface `#241820`, border `#6A3446`, hover `#3A2030`, pressed `#4A2538`.
- Informational: cool blue `#5AA9FF`.
- The user-supplied background image is a first-class decorative layer, not a fixed watermark: its strength is user-controlled and it must be able to reach full visibility. Readability is protected by the chrome opacity floor below, not by permanently dimming the image.

The accent/success split is the load-bearing rule of this palette: a single color must not simultaneously mean “this is the button to press” and “this Mod is on”. Accent answers *what can I do*, green answers *what is true*.

All color tokens in both palettes are declared fully opaque (`#FF……`). Do not introduce decorative gradients, glass blur, neon glow, or arbitrary translucent whites, and never bake alpha into a token. Translucency is applied at runtime by role — see below — plus quiet ghost buttons and subtle disabled states.

### Theme and translucency

- Two themes ship: **暗色** (default) and **亮色**. There is no follow-the-system mode; the choice is explicit and persisted in `AppConfig.Theme`.
- Theme switching repaints the `Color` of the live brush instances held in the application dictionary. It must never swap `MergedDictionaries`: `StaticResource` resolves once at load, so a swap would leave already-rendered elements holding stale brushes. Consequently theme brushes must **not** be frozen.
- Because all mapped brushes — including the `Dialog*` aliases and the `SystemColors.*BrushKey` overrides — bind `Color` to a token, one repaint pass covers the shell, dialogs, and native popup chrome. A new brush must be registered in `AppearanceController.BrushColorTokens` or it will silently stop following the theme.
- Markup must reach every brush through `DynamicResource`. `StaticResource` is a one-shot resolve, so it both freezes the brush when the owning `Style` is sealed and pins the element to the palette that was live at load.
- Repainting the dictionary only fixes markup consumers. Brushes assigned from code (`ToastText.Foreground`, the status dot) or computed once in a view model (`CharacterFilterItem`, `ModCardViewModel`, `LogRow.LevelBrush`) hold an object reference, so `ThemeBrushes` owns one `SolidColorBrush` per token and `ThemeBrushes.Refresh()` repaints those in place after every apply. Handing out the dictionary's own instance is what shipped the 亮色 theme with an invisible toast and a dark 全部 chip.
- View-model brushes are computed without change notification, so a palette switch must also **rebuild** the owning collections (`RefreshView()` / `RefreshLogs()`) and rerun the imperative status paint. This is opt-in via `ApplyAppearance(repaintThemedContent: true)` — the opacity sliders call `ApplyAppearance()` on every tick and must not rebuild the grid.
- Three independent opacity controls exist: **菜单栏** (sidebar), **界面面板** (panels), and **背景图强度** (background image). Sidebar and panel opacity share a readability floor of `0.45`; the background image may go to `0`.
- The floor lives in `AppearancePolicy` and is reused by both the slider `Minimum` and the clamp helper, so UI bounds and stored values cannot drift. A stored value that is out of range or `NaN` is clamped toward full opacity, never toward invisibility.
- Text, borders, and semantic colors always stay fully opaque. Translucency applies to sidebar and panel surfaces only, so status and typography never weaken as the background image is turned up.
- The veil above the background image is driven by the **inverse** of the image opacity. Compositing a dim image under a fixed veil under opaque panels is what previously made the feature invisible; each of those three layers must respond to the setting.

### Typography

- Font stack: `Segoe UI, Microsoft YaHei UI`; no external font dependency.
- Product/page title: 24–28 px semibold/bold.
- Section title: 16–18 px semibold.
- Body/control: 13 px.
- Metadata/captions: 11–12 px.
- Use concise sentence case. Avoid all-caps except the established `ZZZ` mark.

### Shape and elevation

- Corner radii come from tokens, not literals: `ControlRadius` 6 px for controls, `PanelRadius` 12 px for panels/cards, `PillRadius` for compact state chips and filters only. The tighter control radius against the softer panel radius is what separates “thing I click” from “region I read”.
- Padding and toolbar rhythm also come from tokens (`PanelPadding`, `ToolbarPadding`) so density can be tuned in one place.
- Use border and surface separation instead of shadows. Focus uses a visible iris border/ring.
- Controls should normally be 34–38 px high; primary command buttons may be 40 px. `UtilityButton` and `GhostButton` both sit at the 34 px floor.
- `GhostButton` is the quiet inline affordance: no fill until hover. Use it for overflow triggers and expand/collapse toggles so they never compete with a primary action.

## Information architecture

### App shell

- Keep a persistent left sidebar, slightly compact (about 176–184 px) with brand, three destinations, and the `Alt + W` hint.
- Active navigation uses a filled/tinted row, accent marker, icon, and text. Inactive rows remain quiet but readable.
- Keep the bottom status line visible and concise: Mod library path, total Mods, enabled count.

### Home

- Use a compact command header instead of a large hero. Left: page purpose and runtime status. Right: one context-aware primary action and one secondary reload action.
- Runtime status is a labeled status cluster (dot + text + short explanation), not a decorative subtitle.
- Character filters must wrap as compact chips; never use a horizontal native scrollbar. Show label and enabled/total count, with an unmistakable selected state. The chip area is height-capped with an expand/collapse toggle so a large roster cannot push the grid off-screen; capping is done by clipping height, never by nesting a `ScrollViewer`.
- Search, status filter, result count, and refresh belong to one coherent toolbar. Search gets a visible hint.
- Mod cards use a stable three-column layout at 1280 and two columns at 1040. Target roughly 292–300 px wide and 350–366 px tall.
- Card order: preview/state → title and character → capability/runtime note → primary enable/disable action → one overflow entry.
- Enabled cards receive both a success state label and a restrained state border/tint. Warning/error/pending cards use the corresponding semantic color plus explicit text.
- Each card exposes exactly one visible primary toggle plus a single quiet 更多 overflow entry. Maintenance actions (快捷键 / 诊断 / 目录 / 分组 / 删除) live inside that menu, which keeps 删除 out of the primary action's neighborhood and keeps the on-screen control count proportional to the number of cards, not to the number of features.
- Delete is low-emphasis coral, lives at the bottom of the overflow menu behind a separator, and is never adjacent in styling or position to the primary action.
- When filters return no results, show a compact explanatory empty state with a clear way to reset filters.

### Settings

- Keep one safe vertical scroll flow at minimum width.
- Present “游戏与运行核心”, “Mod 导入”, “外观”, and “切换行为” as consistent sections with short descriptions and aligned controls.
- The 外观 section owns theme selection, the three opacity sliders, background-image actions, and a 恢复默认外观 escape hatch. Appearance changes apply live — no restart, no confirmation dialog — so the section belongs to the 立即生效 group.
- Reduce tall empty drop-zone space while preserving drag-and-drop affordance.
- Long paths must remain readable/selectable; action buttons align to their related field.
- Checkbox and close-behavior choices require adequate line wrapping at 1040×680.
- Behavioral caveats are never delivered as one run-on paragraph. Split them into discrete lines, group them under an explicit 立即生效 / 需要重启 distinction, and constrain the reading width so a caveat can be scanned rather than parsed.

### Logs

- Header explains retention briefly; search and actions form one compact toolbar.
- Log list remains dense. Time, level, and message have stable columns; levels use text plus semantic color.
- The log viewport should consume remaining height and keep a visible, usable vertical scrollbar.

## Interaction and accessibility

- Every interactive control has hover, pressed, disabled, and keyboard-focus states.
- Pointer targets are at least 34 px high on this desktop app; destructive actions remain distinct.
- Tab order follows visual order. Enter/Space activation and existing keyboard behaviors must continue to work.
- The card grid is navigable with arrow keys, with Enter toggling the focused card. Tab must not be the only way to cross a grid of hundreds of cards.
- Selected filters and navigation are conveyed through more than color: navigation selection carries an explicit marker plus a weight change, not just a tint.
- Avoid animations that delay state changes. If transitions are used, keep them subtle and under 150 ms.
- Preserve scrolling fixes: thumbs must be draggable, tracks clickable, mouse wheel functional, and content reachable at 1040×680.
- Large libraries must stay responsive: the Mod grid virtualizes its containers and previews are decoded once and cached, so scroll cost stays proportional to what is visible rather than to library size.

## Acceptance criteria

- No horizontal scrollbar in the character-filter area at 1280×820 or 1040×680.
- Primary actions, runtime status, selected character/status filters, enabled/pending/error card states, and page navigation are visually unambiguous.
- All three pages render without clipping or overlapping at both supported sizes.
- Both themes are legible at every allowed opacity setting: at the `0.45` floor with a full-strength background image, card state, semantic colors, and body text remain unambiguous on the light and dark palettes alike.
- Existing behavior and automation names/event handlers remain intact unless a documented replacement is tested.
- Full automated tests pass; visual screenshots and read-only interaction checks pass before release.
